# RAG 2.0 — Knowledge Map Redesign (DW-anchored)

**Status:** Design — pending user review
**Date:** 2026-04-27
**Replaces:** Naive RAG (ChromaDB + chunking + embeddings)
**Primary source:** `.fork_doc/RAG DW lab/day{1,2,3}.ipynb` (DWthon notebooks)
**Secondary context:** `.fork_doc/Karpathy method/` (Karpathy LLM Wiki pattern, DW intro email about Karpathy/Cherny/PageIndex signals)

## TL;DR

Replace the naive RAG stack (chunking → embeddings → top-k vector retrieval) with a DW-style **knowledge map**: a structured, file-backed graph of Sources, Entities, Concepts, and Claims, generated by a deterministic-template + LLM-classifier ingest pipeline, queried via a 5-stage deterministic retrieval pipeline with an agentic fallback for edge cases. The redesign solves cross-document synthesis failures observed in hard evaluations (top_k=8 returning 8 chunks from one dominant source) by replacing similarity search with structural navigation. The application remains a **Learning Lab** — every stage of ingest and retrieval is visible, inspectable, and educational.

## Motivation

The current app teaches naive RAG. Hard evaluation in `backend/tests/rag_evaluation/` exposed a structural flaw: cross-document questions (e.g. "what colors are common to both bedroom and bathroom designs?") returned 8 fragments exclusively from one dominant source. Faithfulness was 10/10 — the system did not hallucinate — but retrieval failed by construction. DW DWthon notebooks identify this as the natural failure mode of `chunking + vector DB` and propose a structurally different approach grounded in three principles:

1. **Templates + LLM-in-rigor** — LLM classifies metadata once via Pydantic structured output; deterministic Python templates assemble the wiki. No LLM-generated content in the wiki layer (this is DW's explicit critique of Karpathy's approach: cost, control, repeatability).
2. **5-stage deterministic retrieval pipeline** — Intent Parser → Candidate Filter → Selection → Context Assembly → Answer. LLM in 3 of 5 stages; Stages 2 and 4 are pure Python over metadata. Pipeline is auditable end-to-end.
3. **Hierarchical "islands with bridges" topology** — entities form islands; cross-entity navigation passes only through Concepts. This produces a readable graph, not "kula makaronu", and structurally enables cross-document synthesis: a Concept node holds claims from multiple sources by construction.

Karpathy's wiki pattern and PageIndex's tree-based retrieval (referenced in DW intro email) are secondary inspirations; the DW notebook implementation drives concrete decisions where they conflict.

## Architecture

Three conceptual layers, Karpathy-style:

```
raw/            (source of truth — immutable; LLM only reads)         → wiki_data/raw/    (gitignored)
wiki/           (LLM-classified, template-generated; structured graph) → wiki_data/wiki/   (gitignored)
schema/         (KNOWLEDGE_MAP.md — conventions, naming rules, workflows) → schema/        (committed to repo)
```

`schema/KNOWLEDGE_MAP.md` is the project's "constitution" (analog to `CLAUDE.md` / `AGENTS.md`) — committed to the repo so it ships with the codebase. `wiki_data/` is gitignored content that grows as users ingest sources. Storage is on disk as JSON/Markdown files. No database (no SQLite, no Neo4j). Files are human-readable, git-friendly, and Obsidian-openable. This honours Karpathy's "the wiki is just a directory of markdown files" while applying DW's templates-not-LLM-generation principle.

## Data model — 4 layers

| Layer | File location | Frontmatter / fields |
|---|---|---|
| **Source** | `wiki/30-Sources/<slug>.md` | `id, title, type, raw_path, ingested_at, source_url?, summary, key_takeaways[], questions[], tags[]` |
| **Entity** | `wiki/20-Entities/<type>/<slug>.md` | `id, type ∈ {Person, Org, Product, Place, Event}, aliases[], description, mentions_count, questions[], tags[]` |
| **Concept** | `wiki/10-Concepts/<slug>.md` | `id, parent_concept?, definition, examples[], related[], questions[], tags[]` |
| **Claim** | line in `wiki/claims.jsonl` | `{id, text, subject_id, source_id, span: {start, end, text}, confidence: 0–1, polarity ∈ {asserts, denies}, related_claim_ids: []}` |

Every artifact carries `questions: List[str]` — the analytical questions it can answer. DW: *"pytania analityczne to złoto dla retrievalu"*. This field is the primary signal for retrieval Stage 2.

## Relations (Edges)

All typed edges live in `wiki/edges.jsonl` (one line = one edge):

```json
{"id": "e_001", "from": "entity:bedroom", "to": "concept:neutral_colors",
 "relation": "associated_with", "source_id": "src_017",
 "span": {"start": 1240, "end": 1318, "text": "..."}, "confidence": 0.87}
```

Closed list of relation types (~10): `mentions`, `defines`, `contradicts`, `supports`, `derives_from`, `instance_of`, `part_of`, `associated_with`, `causes`, `precedes`. Free-form relations are rejected — the agent must know what to ask for.

## Topology rules ("islands with bridges")

From DW day3:
- **Leaves (Sources) have ONE structural link** — to their primary hub (Concept or Entity).
- **Cross-entity routing only via Concepts** — these are the "thin bridges" between Entity islands.
- **Goal:** the graph reads as 5–20 islands with thin bridges, not as kula makaronu.

This topology structurally enables cross-document synthesis: a query about an attribute shared across entities resolves through the Concept layer, which holds claims from multiple sources by construction.

## Provenance invariant

Every claim, every edge, and every assertion in entity/concept descriptions has `source_id + span`. No exceptions. The Lint workflow (Tier 1) enforces this invariant. This is the structural guarantee that protects the wiki from becoming "slop" (DW concern).

## Ingest workflow (5 stages)

LLM in 1–2 stages out of 5. Templates do the rest. Total cost per source: 1 mandatory LLM call + 1 conditional.

| # | Stage | Type | Output |
|---|---|---|---|
| 1 | **Parse** | deterministic | `raw/<slug>/parsed.md` + `manifest.json` (sections, tables, language) |
| 2 | **Classify** | **1 LLM call (Pydantic Structured Output)** | `SourceClassification` — title, description, tags, **questions**, key_takeaways, entity_mentions, concept_mentions, claims, sections |
| 3 | **Resolve + Generate vault** | deterministic (templates) | `wiki/30-Sources/<slug>.md`, create-or-merge `wiki/20-Entities/...`, `wiki/10-Concepts/...`, append `claims.jsonl`, append `edges.jsonl`, regen `index.md/json` |
| 4 | **Conflict detection** | conditional LLM call — runs only when newly-extracted claims have `polarity:denies` overlapping existing `polarity:asserts` on the same subject; otherwise skipped | List of contradictions with explanations (or empty result, no LLM call) |
| 5 | **Save** | deterministic (atomic writes) | All files persisted, append to `log.md` |

### `SourceClassification` Pydantic model (Stage 2 — single LLM call)

```python
class SourceClassification(BaseModel):
    title: str
    description: str
    tags: List[str] = Field(..., description="domain tags for filtering")
    questions: List[str] = Field(..., description="What questions does this source answer?")
    key_takeaways: List[str]
    entity_mentions: List[EntityMention]    # name, type, aliases, span
    concept_mentions: List[ConceptMention]  # name, span, role
    claims: List[ClaimExtraction]            # text, subject, source span, confidence, polarity
    sections: List[SectionSummary]           # title, summary, questions, span
```

### Resolution rules (Stage 3, pure Python)

- **Entity match:** `(type, normalized_name)` exact OR `aliases` contains normalized_name → MERGE; else CREATE.
- **Concept match:** normalized_name match → MERGE; else CREATE.
- **Claim dedup:** hash `(subject_id, normalized_text, polarity)` — append `source_id` if duplicate; never duplicate claim line.
- **Edge dedup:** tuple `(from, to, relation, source_id)`.

### Re-ingest semantics

- **Source page**: overwritten (single source of truth per `source_id`).
- **Entity / Concept**: existing slug → LLM Stage 2 receives current page as context, proposes update (not regen-from-scratch).
- **Claims / Edges**: dedup-by-hash; duplicate appends `source_id`, never new line.

### Review mode

- **Default OFF** for stages 1, 3, 5 (deterministic).
- **Default OFF** for stage 2, but UI shows full `SourceClassification` as diff vs current state — user can roll back before Stage 3.
- **Default ON** for stage 4 — conflicts require judgement; user accepts/rejects per-conflict.
- Global toggle "Review all stages" available.

### Error handling

- **Parsing fail** → status `error` on source, doesn't block other ingests.
- **LLM call fail** → exponential backoff (3 retries), then status `partial` with note in log.
- **Stage timeout** (>60s) → user notice "slow, continue?" + skip option.
- **Save partial** → atomic write (tmp file + rename) prevents corruption mid-save.

## Retrieval workflow (5-stage deterministic pipeline + agent fallback)

```
[1] Intent Parser (LLM, Pydantic)
    → ParsedIntent { entity_mentions[], concept_mentions[], time_period?, intent_type, expected_form }

[2] Candidate Filtering (deterministic Python over index.json + claims.jsonl + edges.jsonl)
    → 10–20 candidates with scores

[3] Selection (LLM, sees only metadata — title, description, questions, tags)
    → top 1–5 most relevant artifacts

[4] Context Assembly (deterministic)
    → markdown context with citation anchors [claim:c_017] [source:s_005]

[5] Answer Generation (LLM, Pydantic)
    → Answer { final_answer, sources, confidence, reasoning_steps, related_questions }
```

### `ParsedIntent` (Stage 1) — DW day3 critical-path

```python
class ParsedIntent(BaseModel):
    original_question: str
    entity_mentions: List[str] = Field(..., description="if none mentioned, return all relevant by tag — never exclude candidates")
    concept_mentions: List[str]
    time_period: Optional[TimePeriod]
    intent_type: Literal['fact_lookup', 'comparison', 'synthesis', 'definition', 'how_to', 'temporal_trend']
    expected_answer_form: Literal['short', 'list', 'table', 'analysis', 'citation']
```

System prompt rules (from DW day3 task):
- "If no entity mentioned — return all candidates from tag (never exclude)."
- "If no time period — fallback to vault-wide span."
- "If question compares multiple entities — `intent_type='comparison'` and all listed in `entity_mentions`."
- "If relative date ('last year') — compute against `date.today()`."

### Stage 2 candidate scoring (deterministic)

- +3 if entity exact match
- +2 if concept match
- +2 if any artifact `questions[]` semantically overlaps (substring, normalized) with user query
- +1 per matching tag
- Time filter on `ingested_at` or content date range

Top 20 → Stage 3.

### Agent fallback

Triggered when:
- Stage 2 returns 0 candidates, **OR**
- Stage 3 confidence < 0.5, **OR**
- Stage 5 confidence < 0.6.

Fallback uses a 10-tool agent loop:

| # | Tool | Purpose |
|---|---|---|
| 1 | `read_index()` | wiki overview |
| 2 | `search_entities(q, type?)` | by name + aliases |
| 3 | `search_concepts(q)` | by name + aliases |
| 4 | `search_wiki_content(q)` | full-text over MD content |
| 5 | `search_text(q, scope)` | full-text over raw/ |
| 6 | `get_node(id)` | full content of entity/concept page |
| 7 | `get_claims(node_id?, query?, polarity?)` | filtered claims |
| 8 | `get_relations(node_id, direction?, type?)` | filtered edges |
| 9 | `read_source(source_id, section?)` | source content with section nav |
| 10 | `query_log(filter)` | temporal queries |

Trace panel shows: 5 pipeline stages + (if triggered) "Pipeline failed at stage X — agent fallback triggered" + each tool call.

## Lint workflow (3 tiers)

Karpathy operation 3 — wiki health check. Protects provenance invariant and navigability.

### Tier 1 — provenance & integrity (deterministic, error severity)

- `provenance_missing` — claim/edge without `source_id` or `span`.
- `dangling_source_ref` — claim/edge points to non-existent `source_id`.
- `dangling_node_ref` — edge points to non-existent entity/concept.
- `corrupted_jsonl` — unparseable lines in `claims.jsonl` or `edges.jsonl`.

### Tier 2 — navigability (deterministic, warning severity)

- `orphan_entity` — entity with no incoming edge and no claim.
- `orphan_concept` — concept with no incoming edges (not bridging anything).
- `missing_backlinks` — edge `A → B` but `B.md` lacks `A` in `mentioned_in`.
- `empty_questions` — empty `questions[]` (retrieval Stage 2 will skip this artifact).
- `empty_description` — page lacks description or <30 chars.

### Tier 3 — semantic (LLM-assisted, info severity, opt-in toggle)

- `unmarked_contradiction` — claims with opposing polarity on same subject without explicit `contradicts` edge.
- `entity_alias_collision` — two entities with very similar names (`Levenshtein < 3`); LLM judges whether to merge.
- `missing_concept` — entity has ≥5 claims on a common topic without a corresponding Concept node.
- `stale_summary` — source.md `summary` predates new claims; LLM compares and proposes update.

### Workflow

1. User clicks **Run Lint** (or `POST /lint/run`).
2. Backend runs Tier 1+2 synchronously, writes report to `wiki/lint_report_<TS>.json`.
3. Tier 3 toggle "Include semantic checks (LLM)" — opt-in, slower, costs tokens.
4. UI lists issues with severity / type / location / description / suggested_fix.
5. Per-issue: **Apply Fix** (deterministic where possible), **Edit & Apply**, **Reject**, **Won't-fix**.
6. Bulk operations available.
7. Append to `log.md`: `## [TS] lint | 47 issues found, 31 fixed, 12 won't-fix, 4 rejected`.

### Suggested fixes (per issue type)

| Issue | Fix |
|---|---|
| `provenance_missing` | UI: "Open source span and select region" — user picks span; system writes `source_id + span` |
| `dangling_source_ref` | "Remove orphan claim/edge" or "Re-link to source X" |
| `orphan_entity` | "Delete" or "Generate stub claims from source mentions" (LLM) |
| `missing_backlinks` | Auto-fix: insert into `mentioned_in` |
| `empty_questions` | "Generate questions" (focused LLM call) |
| `unmarked_contradiction` | "Add contradicts edge" or "Reject (not contradiction)" |

## LLM provider strategy

**Default: OpenAI (gpt-4-class).** Tool calling and Pydantic Structured Output are non-negotiable for Ingest Stage 2 and Retrieval Stages 1/3/5. Open models (Bielik) are immature for tool calling and would derail the agent fallback loop.

`services/llm_service.py` exposes a clean provider interface (`call_llm(messages, response_model?, tools?)`). Swapping to Anthropic Claude or self-hosted Bielik is a documented but not-yet-implemented "bonus track" (~100 LoC + README section).

## Out of scope (explicitly NOT in this redesign)

- **Embeddings as a fallback similarity tool** — DW principle is "deterministic structural retrieval first; add embeddings only if structural fails". We start without; door remains open via `llm_service` abstraction.
- **PageIndex-style per-document tree** — relevant for >100-page PDFs; can be added in v2 as additional optional layer (`wiki/40-DocTrees/`) without restructuring.
- **Bielik / Anthropic provider integration** — `llm_service.py` interface ready, implementation deferred.
- **Multi-language entity merging** — same-entity-different-language merge is manual via Stage 3 review.
- **Reranking models (Cohere etc.)** — overkill at 50–200 source scale.
- **Real-time collaborative editing of wiki** — single-user lab.
